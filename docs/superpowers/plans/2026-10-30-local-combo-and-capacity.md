# Local Model Capacity, Interference Gate, my-coding-lite Combo and Tuning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local llama.cpp model whose capacity is measured and stored in a machine-readable card, that is proven not to slow System One (Laya) or starve the other containers, that OmniRoute serves as the local-only combo `my-coding-lite`, that pi and opencode list as `router-env/my-coding-lite` with the card's context and output limits, and whose configuration is picked by a scripted sweep for the largest usable context first and the best tokens/s second. The sweep ends with a quant headroom check: from the measured VRAM and RAM it decides whether the next quants (for example Q5_K_M, Q6_K) fit at the chosen context, and if so measures them the same way, so the card holds the data for choosing between quants.

**Architecture:**
- Measurements stay where they already are (the `onboard-local-model` skill's `bench-fit.sh`, `effort-run.sh`, `score.sh`, plus a new repo script `scripts/model-interference.sh`). `pylib/capacity.py` merges their JSON outputs, and the `models.yml` entry, into `~/.config/llm-env/capacity/<alias>.json`. It never computes a value that was not measured; unknown values are `null`.
- `pylib/interference.py` turns raw probe files (latency lines, cgroup snapshots, samples) into a pass/fail report and owns the one-line sample format (`append_sample`); the shell script only orchestrates probes and load (Bash orchestrates, Python computes, as in `.agents/architecture.md`).
- `pylib/omniroute_combos.py::ensure_local_combo` creates or updates `my-coding-lite` idempotently, with the card's usable context. `compute_combo_context` resolves `llama-cpp` members only from the card's verified limits (never from the OmniRoute catalog), so `make setup-local-llm-agents` maps the combo while the card is current and drops it when the card is stale or absent; the client side also drops combos whose members are all `llama-cpp` when local inference is off.
- The tuning sweep is a skill script (`tune-sweep.sh`): staged (fit by `llmenv budget`, throughput per ubatch/flash-attn/threads, full-depth verification), each run in its own directory of a git repository under `tmp/model-tune/`, run by a delegated subagent; `tune-pick.sh` ranks; `tune-apply.sh` applies with a backup; the interference gate decides.
- The quant headroom check (`quant-headroom.sh` in the skill, math in `pylib/capacity.py::quant_headroom`) runs after the sweep. It records a fit verdict per larger quant in the card, then fetches (sha256-verified), measures and compares a fitting quant through the same targets, and records the deltas in the card.

**Tech Stack:** bash + shellcheck, `podman` 5.8.9 rootless, `yq`, `jq` 1.8.2, `curl`, Python 3.11+ (`uv run llmenv.py`), pytest (+ xdist), ruff, pyright, llama.cpp `server-vulkan` image (`llama bench`), OmniRoute admin API, pi 1.3.0, opencode 2.0.31.

This plan depends on its make targets (`make llama-enable MODEL=<alias>`, `make llama-disable`, `make start-llama`, `make stop-llama`, the non-disruptive `make start`, `make restart`) and, for the skill tasks only, on its Task 8 edits to the skill: the "Permissions bypassed" Gates paragraph, `scripts/wait-gpu-release.sh`, the `references/models-yml.md` live-phase steps, and the test helpers `_md(path)` / `_section(text, start, end)` in the skill test module. ## Decisions (open questions resolved with defaults)

1. **Card location and lifetime.** `<config dir>/capacity/<alias>.json`, i.e. `~/.config/llm-env/capacity/<alias>.json` (dir 0700, file 0600, atomic write). `make clean` keeps cards (measurement data, like `combo-backups/` and the models). The alias must exist in `models.yml` and match `[a-z0-9][a-z0-9._-]{0,63}` as a whole (`re.fullmatch`, so `"qwen\n"` is refused); otherwise `CapacityError`. This is the first documented exception to the architecture rule that aliases never name files; `bench-fit.sh`'s existing per-run outputs inside a stamp or run-id directory are the second (Task 10 records both).
2. **Usable context.** `usable.context_tokens = min(ctx_size, d + 512)`, where `d` is the deepest depth-sweep point with a measured `tg_tps` (512 = `bench-fit.sh`'s `-p 512` on top of the depth). It is `null` when there is no current depth section, when there is no current interference section (basis `interference not measured`, revised 2026-10-31), or when it has `passed: false`. `usable.max_output_tokens = min(client_max_output_tokens, context_tokens)`, else `null`.
3. **Staleness.** The card stores a fingerprint (first 16 hex chars of the sha256 of the sorted-JSON config snapshot). Each measured section records the fingerprint it was written under; sections with another fingerprint are listed in `stale_sections` and ignored by `usable`. A depth file whose recorded flags differ from the current config is refused at write time.
4. **Combo preconditions.** `ensure-local-combo` creates or updates `my-coding-lite` only when `llm_server.enabled` is true, `llm-server` is running, the `llm-env-local` connection exists, and the card has a current depth section and a current interference section with `passed: true`. Otherwise it reports `skipped` with a reason naming the make target to run, and exits 0.
5. **Combo shape.** Name `my-coding-lite`, strategy `priority`, exactly one member `llama-cpp/<first enabled alias>` with connection `llm-env-local` (no cloud fallbacks, which would lower the floor), `context_length` = usable context. `config` is omitted unless Task 0 shows that OmniRoute requires it. The tool owns the combo: drift (extra members, other context) is overwritten, as for the `llm-env-local` connection.
6. **Interference gate.** It fails when (a) any Laya request returns non-200 during load, (b) Laya p95 during load above an absolute 500 ms (`--max-p95-ms`) or Laya p50 above 150 ms (`--max-p50-ms`) [revised 2026-10-31: Laya serves advisory typed judgments with ~20 s client timeouts, so the original relative rule (p95 > +50 % and > +10 ms, which a 17.7 → 160 ms rise under load tripped) is now only the report field `regression_warning`, never a failure], (c) any `memory.events` `high`/`max`/`oom`/`oom_kill` counter grows for omniroute, remote-setup, system-one, phoenix or llm-server, (d) a container's counters reset (its uptime went down) between the snapshots, (e) no load request completed inside the window, or (f) a service that is `running` in the before-snapshot is not running or missing in the after-snapshot (failure `<service> stopped during the window`; an OOM-killed container that was not relaunched yet has neither counters nor uptime to compare). OmniRoute health latency, VRAM headroom, host MemAvailable and swap delta are recorded but do not gate.
   - **System One disabled:** the script starts no Laya probe and writes no Laya file; (a) and (b) are skipped, the report has `system_one: null` and the note `system_one latency not measured (System One disabled)`, and the card keeps that note. System One enabled but not running: the script refuses ("run 'make start'"), because a pass without Laya would not prove anything about it.
   - **Load:** straight to llm-server (`127.0.0.1:<server.port>`, server key, model = alias), back-to-back requests with `max_tokens` 1024 and a prompt of `min(98304, ctx_size)` bytes. Each request's content starts with a unique prefix `[load <n> <EPOCHREALTIME>] `: llama-server reuses the KV cache of a matching prompt prefix (`cache_prompt` defaults to true, Fact 16), so an identical prompt would be prefilled once and every later request would be decode only. A unique first token leaves only the chat-template header to match, so each request pays a full prefill.
   - **Windows:** 30 s baseline, 120 s load. Laya probe every 0.25 s, OmniRoute `/api/monitoring/health` every 1 s, snapshot every 5 s (probe and sampler loops run a fixed number of iterations: seconds / interval, at least 1). The load loop stops itself at the window end, and each request has `curl --max-time` = seconds left in the window (at least 1), so no request outlives the window. When one request takes longer than the window, (e) fails with `no load request completed within the window; rerun with a larger --seconds`. The warm-up chat is bounded the same way (`--max-time` = the load window): a non-200 or timed-out warm-up stops the script before any measurement with `warm-up chat failed (<http_code>); rerun with a larger --seconds`, since a load request (the same prefill plus 1024 tokens) could not finish either.
   - **Samples:** each 5 s snapshot is one compact JSON line appended by Python (`llmenv interference snapshot --append <file>`, `pylib.interference.append_sample`), never the CLI's pretty-printed stdout (`emit()` uses `indent=2`, Fact 19).
7. **Tool-call reliability.** Measured from pi's `tool_execution_end` events (`isError`) in the L3-L5 effort-run transcripts. It includes legitimate command failures; the card labels it `tool_error_rate`, not "malformed calls".
8. **Ladder lane.** `effort-run.sh --model router-env/llama-cpp/<alias>` with `PI_CODING_AGENT_DIR=$HOME/.pi/agent`: the profile `make setup-local-llm-agents` writes. It does not depend on the combo existing. `effort-run.sh`'s default profile stays unchanged.
9. **Tuning depths and selection (one rule for the sweep, the pick, the card and the quant trials).**
   - Reference depth `R(ctx) = min(131072, ctx - 512)`; full depth `F(ctx) = ctx - 512`.
   - Verify-stage depths: `0, 32768, R, F`, dropping values above `F`, deduplicated, ascending. ctx 131072 → `0,32768,130560`; ctx 196608 → `0,32768,131072,196096`; ctx 262144 → `0,32768,131072,261632`.
   - Candidates are verify-stage rows with status ok, a measured `tg_tps` at `F`, `model_vram_mib <= vram_available_mib` (both in the row; `vram_available_mib` is `llmenv budget`'s `available_mib` with llm-server stopped), and `tg_tps` at `R` of at least 20 t/s (`--min-tg 20`). Throughput-stage rows are not candidates and are not listed as rejected.
   - Rank: ctx descending, then `tg_at_ref` descending, then `pp_at_ref` descending. Reject reasons, checked in this order: `failed`, `not verified to full depth`, `model VRAM over budget`, `tg at reference depth below 20`.
   - If the gate fails, the next ranked row is tried (at most 3), then the backup is restored. Threads are swept only when `n_cpu_moe` is set and are reported, not applied (no preset key exists). Flash-attention off with a quantized KV cache is attempted and recorded as `failed` if llama.cpp refuses it (measured, not assumed).
10. **Benchmarks run under production limits, with Laya held resident.** `bench-fit.sh` passes `--cpus`/`--memory` from `llmenv resources` (`llm_server.cpus`, `llm_server.memory_mib`) when they are positive, so MoE offload numbers reflect the RAM and CPU llm-server really gets. `model_vram_mib = peak - first` is whole-GPU arithmetic (Fact 7), and Laya frees about 3.7 GB after 600 s idle and reloads on the next request, so a Laya unload or reload during a bench would shift it by gigabytes. When `system_one.enabled` is true and `system-one` runs, `bench-fit.sh` sends one Laya request before the GPU sampler starts and one every 60 s until the bench ends (a background loop the trap kills), and records `system_one_warm: true` (else `false`). The tuning procedure never runs the repo's Vulkan benchmark target (`scripts/benchmark.sh`): on a Vulkan failure it rewrites `gpu.backend` to `cpu` in the live `models.yml` (Fact 17), and the verify run already measured the applied configuration.
11. **`llama-cpp` members resolve only from current cards, never from the catalog.** `_resolve_member_context_window` falls back to the `/v1/models` catalog by `root` (`pylib/omniroute.py:458`), and OmniRoute lists `llama-cpp/<alias>` there (`.agents/architecture.md`); whether that entry carries a `context_length` is Task 0 finding (a). The rule is the same for both outcomes: a `llama-cpp` member takes `context_window` and `max_output_tokens` from `local_limits[alias]` when `local_limits` lists it, and both are `None` otherwise (alias missing from `local_limits`, or no `local_limits` at all). The catalog is never read for `llama-cpp`.
    - (a) shows no context: nothing observable changes beyond what Task 6 adds.
    - (a) shows a context: a stale or absent card still leaves the member unresolved, so `my-coding-lite` has a null minimum and local clients drop it (`setup-local-llm-agents.sh` skips a null minimum).
    - Remote installer: cards are not mounted into `remote-setup`, which calls `compute_combo_context` without local limits, so its `llama-cpp` members are unresolved in both outcomes and `_build_unified_models` skips `my-coding-lite` (null minimum).
    - Mixed combos: an unmeasured `llama-cpp` member is left out of the minimum, as any member without a known window is today.
    - Task 0 findings (a), (f) and (g) set only the README wording, because the rule makes the code independent of them.
12. **router-env client defects (both still reproduce, Fact 4).** The key goes to `${XDG_CONFIG_HOME:-$HOME/.config}/router-env/api-key` (dir 0700, file 0600, no trailing newline), copied from the private `$api_key_file` (never through argv or jq). pi gets `"apiKey": "!cat '<absolute path>'"` (the path must not contain `'`, else die), opencode gets `"apiKey": "{file:<absolute path>}"`. pi `enabledModels` becomes the current router-env ids in setup order, followed by the prior non-`router-env/` entries in their order, without duplicates. This mirrors the existing OpenCode favorites rule; the QUICK_START sentence and its doc test change with it.
13. **Scope.** One plan (owner request), reviewable in order as groups: Tasks 1-4 (measurement and card), 5-6 (combo and client mapping; need Task 4), 7 (client defects; independent), 8-9 (tuning and quants; need Tasks 1, 3, 4 and 5), 10 (docs), 11 (live onboarding of the acceptance model; no repo change), 12 (final verification and live acceptance, last).
14. **Quant headroom (owner addition).**
    - Candidates are the next quants in the same Hugging Face repo at the same commit as the entry (default `--quants Q5_K_M,Q6_K`). Sizes and `lfs.oid` come from the HF tree API at that sha, never from constants, and so does the current quant's own record (`current`): the entry's `size_bytes` may be rounded (Fact 15), so it is never used for `delta`.
    - Candidate file: the entry's `file` path with its `quantization` token replaced by the candidate quant (case-insensitive). If that exact path is in the tree, it is a single-file candidate. Otherwise, if a tree path containing the quant token matches `-[0-9]{5}-of-[0-9]{5}\.gguf$`, the reason is `sharded, not supported`; otherwise `not in repo`.
    - Math: `delta = ceil(cand_bytes / MiB) - ceil(current_bytes / MiB)`, `predicted_vram = measured model_vram_mib + delta`, and VRAM fits when `predicted_vram <= vram_available_mib`. `vram_available_mib` is `llmenv budget`'s `available_mib` (which already holds the 1024 MiB spike headroom and the System One and compositor reserves), read with llm-server stopped: `check` refuses `llmenv budget` while llm-server runs and then takes `--vram-available-mib` (the applied tune-pick row's value), because `cmd_budget` counts the whole GPU's used VRAM as compositor use when the compositor shares the GPU (Fact 18). RAM fits when `llm_server_peak_mib + delta <= llm_server_cap_mib` and `host_available_min_mib - delta >= 4096` (`HOST_MEMORY_FLOOR_MIB`).
    - Unknown RAM or an `n_cpu_moe` offload gives `fits: null` with a reason, never a guess. The verdict `no headroom for Q5_K_M/Q6_K at ctx N, free MiB X` (X = `vram_available_mib - model_vram_mib`) is written only when every candidate is known not to fit.
    - An entry URL pinned to `resolve/<40-hex sha>/` uses that sha. A `resolve/main/` URL is resolved to the current sha only when the entry's `size_bytes` equals that file's size in the tree at that sha; otherwise the check refuses ("pin the entry url first").
    - Fitting candidates are trialled in ascending size, at the same sweep point (same runtime keys, `ctx_size`, `n_gpu_layers`), the same depths (Decision 9) and the same ladder (L1-L5, same efforts). The first one that fails the interference gate stops the trials. The default quant is not switched: the trial ends by restoring the original alias, and switching is the owner's call (under bypass: announce the comparison table and keep the original).
    - `my-coding-lite` is unavailable while a candidate is served.
15. **Acceptance model (round 2).** The live acceptance runs on Ornith-1.5-9B Q4_K_M, alias `ornith-15-9b`, a dense model (no `n_cpu_moe`), because the enabled `ornith-35b` has `n_cpu_moe: 28` and Decision 14 then gives every candidate `fits: null`, so neither a verdict nor a trial could appear. Task 11 adds the entry from the already-downloaded file with the skill's backup-then-add rule (sibling-edited `references/models-yml.md` live phase, here validated before the rename) and enables and serves it with the sibling plan's targets (`make llama-enable`, `make start-llama`), skipping the repo's Vulkan benchmark target (Decision 10): repo `ornith-ai/Ornith-1.5-9B-GGUF` pinned at commit `abdd624b12ebf020b767fff532ff44fe552b28c3` (from `tmp/model-scout/20261030-ornith15-9b/url.txt`, equal to the API's current `.sha` on 2026-10-30), file `Ornith-1.5-9B-Q4_K_M.gguf`, `size_bytes: 5780090816` (tree `size` and `stat` agree), `ctx_size: 131072` as the starting point (the sweep then tries 196608 and 262144), `client_max_output_tokens: 8192`. The host stays in local-inference mode afterwards (`my-coding-lite` needs llm-server); returning it to gateway-only (`make stop-llama`, `make llama-disable`) is the owner's call.
